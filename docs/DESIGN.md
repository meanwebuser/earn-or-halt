# Design

## Два контура

### 1. Economic runtime

Runtime — обычный наблюдаемый процесс. Он принимает задания, создаёт результат, записывает фактическую стоимость и подтверждённую выручку. Перед каждой потенциально платной операцией `EconomicPolicy` выдаёт решение `continue` или `halt`.

Halt сохраняется в SQLite. Это специально не retry/pause: перезапуск контейнера не должен бесконечно сжигать деньги после экономического провала.

### 2. Signed bootstrap

Seed не доверяет transport. Blockscout, HTTPS, IPFS и IPNS лишь сообщают, где лежит релиз. Доверие создают:

1. зафиксированный public key;
2. SHA-256 точного архива;
3. ECDSA-подпись точного архива;
4. безопасная распаковка;
5. атомарное переключение `current` symlink.

## Почему подпись не ставится на восстановленный JSON

Две корректные реализации JSON могут сериализовать один объект разными байтами. Подпись поля `manifest without signature` ломается из-за пробелов, Unicode, порядка ключей и разделителей. В этом проекте подпись относится к неизменяемому `release.tar.gz`, а manifest содержит только transport metadata.

## Почему release key отделён от Ethereum key

Ethereum key отвечает за публикацию pointer. Release key отвечает за разрешение исполнения кода. Компрометация publisher key не должна автоматически разрешать атакующему подписывать исполняемый релиз.

## Почему runtime не самоперепаковывает код

Самоизменяющийся runtime смешивает deployment authority с бизнес-логикой, усложняет rollback и делает компрометацию процесса постоянной. Runtime подписывает и сохраняет state локально через транзакционную SQLite, а релиз создаётся отдельным операторским pipeline.

## State machine

```text
starting -> idle -> evaluating -> working -> running
                              \-> halted
signal/operator -------------> stopped
```

## Ledger semantics

- `revenue`: подтверждённая выручка за успешно выполненную задачу;
- `credit`: внешний стартовый или дополнительный кредит;
- `cost`: фактическая стоимость операции;
- `refund`: уменьшение учтённой выручки.

Стартовый кредит policy не хранится как ledger event: это отдельный лимит риска, заданный конфигурацией.
