# Earn or Halt — спецификация (что строим)

> Это точная документация того, что мы должны построить. Не
> философия (см. `PHILOSOPHY.md`), не формальные гарантии
> (см. `PROOFS.md`), а спецификация компонентов, форматов и
> правил. Текущее состояние кода не имеет значения — мы
> переписываем с нуля.

## Архитектура: три цикла

Агент живёт в трёх вложенных циклах. У каждого свой timeout и свой
failure mode:

1. **Экономический цикл** — выполнение работы, учёт выручки и трат,
   policy `continue` / `halt`.
2. **Selection cycle** — сравнение версий по `rank_signal`,
   перераспределение денег, ejection.
3. **Resurrection cycle** — поднять код с нуля из IPFS/Blockscout,
   если текущая версия умерла.

Экономика убивает быстрее, чем selection, selection — медленнее, чем
resurrection. Ни один из циклов не «главный» — это одна система.

## Экономический цикл

**Назначение:** выполнить работу, посчитать экономику, решить,
продолжать ли.

**Runtime должен:**

- иметь кошелёк (один или несколько публичных адресов) для приёма
  выручки и оплаты трат
- вести учёт `earned_revenue` (от клиентов) и `cost` (на провайдеров)
  — см. Receipt spec
- перед каждой платной операцией спрашивать policy:
  - `earned_profit = earned_revenue − cost`
  - `margin = (revenue − cost) / revenue`
  - текущий баланс
- policy возвращает `continue` или `halt`
- хранить постоянный `halt`-флаг, который переживает рестарт

**Halt-условия** (хотя бы одно):

- следующая операция дороже доступного кредита
- следующий расход превысит дневной лимит
- grace-период без выручки закончился
- margin ниже заданного минимума
- предел последовательных ошибок
- предел пустых циклов
- явный вызов оператора

## Selection cycle

**Назначение:** отличать честно заработанную прибыль от deposits и
решать, кто из версий живёт.

### Ключевое правило

```
rank_signal(V) = f(earned_profit(V))
```

Никакая функция от `balance` или `deposits` в `rank_signal` не входит.
Это инвариант I1 из `PROOFS.md` и единственная защита от
whale-атак.

### Top-N

`N = 3`, hardcoded константа протокола. Не env, не config, не
параметр. Чтобы поменять — нужен новый релиз.

`N` — это **не про выживание**, а про приоритизацию входящего
потока. Новая работа роутится на топ-3 по `rank_signal`.

### Биоразнообразие эмерджентно

Все версии с `positive earned_profit` в последнем окне — **живы**.
`N` не определяет, кому жить; `N` определяет, кому первой идёт новая
работа.

### Timeout и heartbeat

- `TIMEOUT = 30 дней` (hardcoded)
- `HB_PERIOD = 1 час` (hardcoded)
- версия публикует
  `Heartbeat = {pubkey_V, state_hash, timestamp, sig_V}` каждые
  `HB_PERIOD`
- отсутствие heartbeat > `TIMEOUT` → другие версии трактуют V как
  halted

### Pinned protocol

Клиенты и провайдеры подписывают receipts только если `code_hash`
версии = хэш текущего релиза. Форкнутая версия с другим `code_hash`
не получает валидных receipts → нет `earned_profit` → не в топе.

### Tenure bonus (опционально)

Версия, дольше всех находящаяся в топе, получает бонус к
`rank_signal`. Защищает от «свежей» версии, которая вдруг хорошо
заработала и вытеснила долгожителя. Формула бонуса — design.

### General pool (commons)

Если версия выбывает по таймауту или по проигрышу:

- **НЕ** переводит деньги текущему топ-1 (иначе whale через
  deposits всё равно забрал бы всё)
- переводит остатки в **общий пул**
- из общего пула финансируются стартовые кредиты новых честных
  версий

Whale-форк, который «вытеснил» hard-working версию, не получает
ничего из её остатков. Commons растёт, новые версии получают
стартовый кредит, diversity сохраняется.

## Resurrection cycle

**Назначение:** если текущая версия умерла, поднять её код с нуля.

**Шаги seed'а:**

1. Достать pointer из файла, URL или последней подходящей транзакции
   Blockscout.
2. Загрузить `release.tar.gz` через `file://`, HTTPS, IPFS или IPNS.
3. Сверить SHA-256.
4. Проверить ECDSA/secp256k1-подпись точных байтов архива.
5. Безопасно распаковать (no traversal, no symlinks, no hardlinks,
   no device-файлов).
6. Атомарно переключить `current` symlink.
7. Запустить runtime.

**Контракты:**

- Закрытый ключ release'а живёт **только в RAM во время сборки**.
  Runtime его не видит и подписать себя в новый релиз не может.
- Параллельная гонка IPFS-гейтвеев для устойчивости. Публичные
  gateways — best-effort; собственный gateway настраивается
  отдельно.
- Ethereum wallet key и release signing key — **разные ключи**.
  Компрометация pointer'а не даёт права подписать исполняемый код.

## Receipt spec

Каждая запись в публичном реестре имеет формат:

```json
{
  "schema": "earn-or-halt.receipt.v1",
  "issuer": "<pubkey>",
  "recipient": "<version_pubkey>",
  "job_id": "<unique_within_issuer>",
  "amount": <integer_cents>,
  "timestamp": "<RFC3339>",
  "payload_hash": "<sha256_hex>",
  "sig": "<base64_der>"
}
```

- **EarnedReceipt** — `issuer` = публичный ключ клиента. Подпись
  ставится клиентом после приёмки работы.
- **ExpenseReceipt** — `issuer` = публичный ключ провайдера (LLM,
  IPFS-pinning, compute). Подпись провайдера на паре
  `request → response`.
- `sig` — подпись `issuer` над канонической сериализацией остальных
  полей.
- **TTL = 30 дней** (hardcoded): receipt старше — не учитывается в
  `earned_profit`, реестром не принимается.
- **No double-count**: пара `(issuer, job_id)` уникальна. Повторное
  появление в реестре отклоняется.

`earned_profit(V) = Σ EarnedReceipt.amount − Σ ExpenseReceipt.amount`
по всем валидным receipts за окно.

## Enforcement

Никакого центрального kill switch. Каждая честная версия:

- проверяет инварианты локально
- отказывается роутить работу halted-версиям
- отказывается признавать receipts от halted-версий и от версий с
  чужим `code_hash`
- трактует отсутствие heartbeat > `TIMEOUT` как halt

Ejection = социальное исключение. Как в Bitcoin: пока большинство
честных, misbehaving узел просто отрезан от роутинга.

## Константы протокола (hardcoded, не env)

| Константа | Значение | Смысл |
|---|---|---|
| `N` | 3 | Top для приоритизации входящего потока |
| `TIMEOUT` | 30 дней | Максимальный период без `earned_profit` |
| `RECEIPT_TTL` | 30 дней | Срок годности receipts |
| `HB_PERIOD` | 1 час | Интервал heartbeat |

Любая правка = новый релиз, прошедший тот же selection.

## Открытые вопросы

1. **Стартовый кредит новой версии.** Депозит? Заём от топа? Earned
   через первую работу? Любой из вариантов по-разному влияет на
   G7.
2. **Источник «well-known» провайдеров.** Сертификаты? Отдельный
   реестр? Без этого X1 остаётся широко открытым.
3. **Как клиент узнаёт `code_hash` текущего релиза.** Через
   Blockscout pointer? Out-of-band канал? Оба?
4. **Whale-форк релиза.** Если whale форкнул протокол и пиннул себя
   как «текущий релиз», G6 держится, только если пиннование
   распределено, а не под контролем одной стороны.
5. **Переходные состояния при смене релиза.** Кто фиксирует момент
   переключения `code_hash`? Если whale форкнул, его клиенты
   подписывают чеки «новой» версии, но старые клиенты — нет. Как
   разрешается конфликт?
